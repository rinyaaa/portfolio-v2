# 実装レビュー / 受け入れ判定

実装した本人（同じセッションのClaude）が「直したのでOK」と自己判断で完了にしないための手順。判定の根拠は**成果物と計画書だけ**で、実装時の意図や事情は根拠にしない。

このスキルは組み込みの `/code-review`（バグ・簡素化・効率の観点でコードを読む）を置き換えるものではない。`/code-review` を呼ぶ側に回り、**計画書との突き合わせと受け入れ判定**を担う。

## Step 1: レビューの深さを決める

変更規模で段階化する。全ての変更に別エージェントを立てると、そのたびに文脈を読み直すためコストが跳ね上がる。

| 条件 | レビューの方法 |
| --- | --- |
| 数十行以内 / 単一ファイル / 既存パターンの踏襲 | **セッション内** — `/code-review` を1回 + Step 3のチェックリスト照合 |
| 複数ファイル / 新規モジュール / 依存追加 / 挙動の変更 | **別エージェント** — Step 2 |
| 安全網（`.claude/settings.json`・`.claude/hooks/`・`AGENTS.md`）に触る | **別エージェント**（規模によらず） |
| 認証・認可・個人情報・課金・外部公開に触る | **別エージェント** + `go-live-checklist` |

迷ったら重い方を選ぶ。ユーザーが「軽く見て」と言えばセッション内に落としてよい。

## Step 2: 別エージェントに依頼する

Agentツールで `impl-reviewer`（同梱のレビュー担当。`.claude/agents/impl-reviewer.md`）を起動する。モデルとツールはそちらの frontmatter で固定してあるので、**呼び出し側でモデルを指定しない**。

**渡すものは3つだけ。いずれも「探しに行かせる」のではなく、内容そのものをプロンプトに入れる。**

1. 計画書の**本文**（`docs/plans/` にあるなら中身をそのまま。無ければスコープ / スコープ外 / 受け入れ条件を明文で）
2. **`git diff` の出力そのもの**（大きすぎる場合は `git diff --stat` ＋ 主要ファイルの diff。「変更ファイル一覧」だけを渡して読ませない）
3. Step 3のチェックリスト（プロジェクト固有の観点を足したなら、それも）

**ここをケチると高くつく。** 「計画書を読め、差分を見ろ、新規ファイルを読め」と指示すると、レビュー担当は探索から始めてトークンを大量に使う。材料を渡してあれば、読む作業がそのまま省ける。

ファイルを開かせてよいのは、**差分だけでは判断できない箇所**（差分の周辺の既存コード、参照先の実体があるかの確認など）に限る。その旨をプロンプトに明記する。

**渡さないもの**: 実装時の判断理由、「時間が無かった」等の事情、こちらの自己評価。これらを渡すと、レビュー担当が結論を追認する方向に引きずられる。

## Step 3: チェックリスト

観点ごとに**満たす / 満たさない**を判定し、**根拠（該当箇所のファイル名と行）を必ず添える**。点数は付けない。

| 観点 | 満たす | 満たさない |
| --- | --- | --- |
| 要件を満たしているか | 受け入れ条件を全て満たし、確認方法も示されている | 満たしていない条件がある / 満たしたかどうか確認していない条件がある |
| スコープ外のことをやっていないか | 計画の範囲内だけ | 合意していない変更が含まれる（軽微でも、説明が無ければ満たさない） |
| 不要なコードを生成していないか | 無い | 使われないヘルパー・過剰な抽象化・コメントアウトの残骸・死んだコードがある |
| テストが通っているか | 新規・既存とも通り、変更を検証するテストが追加されている | 失敗している / 実行していない / 新規テストが無い（書けない理由と手動での確認方法が明記されていれば満たす） |
| 禁止事項に抵触していないか | 無い | `AGENTS.md` の安全ルールに反する / 判断が微妙な箇所を人間に上げないまま通そうとしている |

**受け入れの条件: 満たさない観点が1つも無いこと。** 1つでもあればStep 4へ。

**「ほぼ満たしている」は満たすに入れない。** 計画書に数値や条件として書かれたものは、わずかでも下回れば満たさない（例:「テストが全件通ること」に対して1件失敗、「N件以下に収める」に対してN+1件）。ここを甘くすると、受け入れ条件を書いた意味が無くなる。

### 観点をこのプロジェクト用に決める

上の5つは既定で、どのプロジェクトでも成立する。**これに加えて、`CLAUDE.md` §8「コーディング規約 / Claude への指示」と §9「Claude Code固有の補足」に書かれている約束を観点として足す。** このリポジトリで実際に効くのは次の4つ。

- **見た目**: Figma（`portfolio-design-source`）を確認した上での実装か。色・サイズを推測で置いていないか。あわせて `ui-guidelines` の制約（タッチ操作・コントラスト）を満たしているか
- **層の分け方**: microCMS依存が `src/lib/microcms.ts` に閉じているか。pages/componentsが生レスポンスではなく正規化済みの `Post` を受け取っているか
- **JSの重さ**: インタラクティブが不要なものを React island にしていないか。`client:load` を `client:visible` で足りる箇所に使っていないか
- **推測で埋めていないか**（CLAUDE.md §9.3）: プロフィール文・実績・技術スタック一覧・SNSリンク等、本人に確認しないと分からない内容を自分の判断で埋めていないか。SEO（title/meta/構造化データ/alt）を下げていないか

`CLAUDE.md` に該当する記述が無い領域については、**推測で観点を作らず既定の5観点だけで判定し、その旨を報告に書く**。

観点を**減らす**のは、そのプロジェクトで原理的に成立しないときだけ（例: 実行環境が無くテストを書く手段が無い）。「面倒だから」では減らさない。追加・削除したら `CLAUDE.md` に書いて固定する——セッションごとに観点が変わると、前回通ったものが今回落ちる。

## Step 4: 修正ループ

1. `impl-reviewer` が**修正チケット**を出す（観点 / 何が問題か / どう直すか / 該当箇所 / **解消の確認方法**）
2. 実装担当がチケットに沿って修正する
3. **`impl-reviewer-recheck`（`.claude/agents/impl-reviewer-recheck.md`）に差し戻す。** 実装担当が「直したのでOK」と自己判断で完了にしない
4. ループは5回まで。超えたら自力で解決しようとせず、何が解決できていないか・どこで詰まっているかを添えて人間に報告する

**再レビューに渡すのは、チケットと修正分の差分（`git diff` の出力）だけ。** 全体をもう一度検証させない——初回と同じ材料を渡すと、同じ作業をもう一度やることになる（実測で、範囲を絞らなかった再レビューは初回より高くついた）。

再レビュー担当は初回の文脈を持たない別のエージェントなので、**チケットの「解消の確認方法」が判定の唯一の材料**になる。ここが曖昧だと、結局全部読み直すことになって安くならない。

全チケットが解消したら受け入れ。未解消があれば実装担当に戻す（2へ）。

指摘に反論がある場合は、実装担当が握りつぶさず人間に上げる。レビュー担当が間違っていることもあるが、判定するのは人間。

## Step 5: 結果を伝える

- 観点ごとの判定（満たす / 満たさない）と根拠、受け入れ可否
- 受け入れた場合は、次に `work-log` で記録を残すことを案内する
- エージェントのレビューを通ったものだけを人間のレビューに回す（2次レビューは人間）
