# 作業記録（history）

**同じ詰まり方を二度しない**のが目的で、進捗報告書ではない。

**重要な前提**: `docs/history/` は、次のタスクを始めるときに読まれない。読む仕組みを意図的に作っていない（大半の記録は次のタスクと無関係で、毎回読むとコストだけがかかるため）。したがって**記録を書くこと自体では、次回の挙動は変わらない**。挙動を変えるのは Step 3 の昇格だけ。ここを飛ばすと、この作業は人間向けのログを書いただけで終わる。

## いつ書くか

レビューを通って作業が一区切りしたとき。PRを出したなら、マージを待たずに書いてよい。

**書かなくてよいもの**: タイポ修正、設定値の変更、調査だけで終わった依頼。詰まりも知見も無い作業を記録しても、後から読む人のコストになるだけ。

## 書き方

`docs/history/YYYY-MM-DD-<タスクの短い名前>.md`（日付は `date +%F` で取る）。同じ日に複数あればファイルを分ける。

```markdown
# YYYY-MM-DD タスク名

## やったこと
（何を変えたか。ファイル名は具体的に。PR・issueがあればリンク）

## 詰まった点 / 解決方法
（詰まらなかったなら「特になし」でよい。**なぜそうなったか**まで書く——
 「Xで失敗した→Yで直した」だけだと、次に同じ場面で再現できない）

## 次回への申し送り・知見
（次に同じ領域を触る人が知っていると得をすること。
 未解決のまま残したこと、意図的に先送りした判断とその理由）
```

## Step 1: 材料を集める

`git log --oneline` と `git diff --stat`（またはPRの差分）で、実際に何が変わったかを確認する。**会話の記憶だけで書かない**——やったつもりで終わっていることがある。

## Step 2: 書く

上のテンプレートに沿って書く。長さは1タスクあたり画面1つ分で足りる。作業の実況（「まずAを試して、次にBを試して」）は要らない。**結論と、次の人が知る必要のあることだけ**を残す。

## Step 3: 効く知見を昇格させる（この手順の本体）

**ここを飛ばすなら、記録を書く意味はほぼない。**

今回の「詰まった点」と「申し送り」を1つずつ見て、**事実か傾向か**を分ける。昇格のタイミングが違う。

- **事実** — このプロジェクトはこうなっている、という確定した情報（「ワークツリーごとにDBが別ファイルになる」「起動は◯◯」）。**1回目で昇格する。** 事実は1回で確定するので、2回目を待つのは*わざともう一度同じ失敗をする*こと
- **傾向** — 自分がよく忘れる・よく指摘される、という癖（「レビューでスコープ外を指摘されがち」）。**2回目で昇格する。** 1回だけなら、たまたまその日の話かもしれない。過去に同じことが書かれているかは、**読まずに `grep` で探す**（下記）

迷ったら「**同じ状況に置かれた他人も踏むか**」で切る。踏むなら事実（1回目で昇格）、自分だけの癖なら傾向（2回目で昇格）。

### 傾向の2回目を、読まずに判定する

**過去の記録を開いて読まない。** 候補の語で検索し、**当たったファイルだけ**開く。

```bash
grep -rln "スコープ外\|範囲外" docs/history/    # 表現のぶれは | で並べる
```

- **0件** → 今回が1回目。昇格しない。ここで終わり（開くファイルはゼロ）
- **1件以上** → そのファイルだけ開いて、同じ傾向かを確認してから昇格する

記録は1件2,000〜4,000文字あるので、「直近数件を読む」と毎回7,000トークン前後かかり、当たらなければ全部無駄になる。grepなら外れたときのコストがほぼゼロで済む。

表現がぶれて当たらないことはある（「スコープ外」と「範囲外」）。**それは許容する**——昇格が1回遅れるだけで、次に同じ指摘を受けたときにまた判定される。確実性のために全件読むほうが割に合わない。

判定したら、1〜2行に削って下表の反映先へ移す。

| 知見の種類 | 何回目で昇格 | 反映先 |
| --- | --- | --- |
| プロジェクト固有の約束事（層の分け方、命名、起動手順、環境の癖） | **事実 / 1回目** | `CLAUDE.md` |
| 特定の作業でしか出てこない手順・注意点 | **事実 / 1回目** | 該当するスキル、または新しいスキル |
| 安全に関わること（消してはいけないもの等） | **事実 / 1回目** | `AGENTS.md` の安全ルール + 可能なら `permissions.deny` |
| レビューで繰り返し受ける同種の指摘 | **傾向 / 2回目** | `implementation-review` のチェックリスト |
| 繰り返し忘れる段取り | **傾向 / 2回目** | 該当するスキル |

反映先が `AGENTS.md` や `.claude/settings.json` になる場合は、**安全網の変更なので勝手に書き換えず**、何をどう変えるか提案してユーザーの確認を得る。

事実・傾向のどちらであっても、昇格させるのは「次に同じ場面が来る」ものだけ。今回限りの事情（この日たまたま環境が壊れていた等）は、事実であっても昇格させない。理由はトークンではなく**希釈**——`CLAUDE.md` に些末なものを入れるほど、本当に守るべきルールがその中に埋もれる。1行に削れないものは、たいてい昇格に値しない。

昇格させたものは、記録側に「→ `CLAUDE.md` に昇格」と1行添える。同じ知見を次回また昇格させようとするのを防ぐため。

## Step 4: 索引を更新する

`docs/history/README.md` があれば1行追加する。無ければ作らなくてよい（記録が数件たまってから `doc-index` スキルで作る）。
