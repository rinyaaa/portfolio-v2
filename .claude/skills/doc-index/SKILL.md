# ドキュメント索引の書き方

ドキュメントが増えると、AIも人も「どれを読めばいいか」が分からなくなり、結局全部読むか何も読まないかになる。索引の1行に**参照タイミング**か**扱わない範囲**を必ず入れることで、全部を常に読ませずに済ませる。

## 1行の型

```
* `パス` は〈内容〉の〈区分〉です。〈いつ参照するか、または 何に使わないか〉。
```

区分は3つだけ。

- **正本** — そこに書かれていることが仕様・設計の根拠になるもの
- **説明** — 読み手に向けた解説。根拠には使わない
- **記録** — 起きたことの記録。仕様ではない

後半は必ず1つ入れる。全部を常に読ませないための条件、または誤用を先回りで止める一文。

## 記載例

```markdown
* `ARCHITECTURE.md` はシステム構成・責務・処理経路・データ境界の正本です。複数レイヤーにまたがる変更では、最初に必要な章だけ参照してください。
* `docs/architecture/` はサブシステム固有の設計の正本です。全体像は持たないので、`docs/architecture/README.md` の索引から必要なファイルだけ辿ってください。
* `README.md` は公開向けの概要・起動手順の説明です。内部設計の根拠には使いません。
* `docs/manual/` は利用者向けの説明です。実装の責務や内部挙動の確認には使いません。
* `docs/knowledge/` は再利用可能な知見の記録です。仕様ではなく、作業ログや一時的な状態も追加しません。
* `docs/decisions/` は技術判断（ADR）の記録です。判断を変えるときは、既存ADRの理由と影響を更新してください。
```

## 書くこと / 書かないこと

**書く**

- 参照タイミング（例:「複数レイヤーにまたがる変更では」「UIの変更時は」）
- 扱わない範囲（例:「内部設計の根拠には使わない」「作業ログは追加しない」）

**書かない**

- 特定バージョンや特定機能に紐づく記述（すぐ古くなる）
- 詳細ドキュメントの中身の要約（索引に書けば足りる。二重管理になり、片方だけ古くなる）

## 適用手順

1. 実在するドキュメントを列挙する（`find . -name "*.md" -not -path "./node_modules/*"` 等）。**索引に書いてあるが存在しないファイル**が無いかもここで確認する
2. 各ファイルを 正本 / 説明 / 記録 のどれかに割り当てる
3. 割り当てられないものは統合するか移動する。**どれでもないドキュメントは、たいてい役割が決まっていないだけ**なので、ユーザーに何のためのものか確認する
4. 上の型で1行ずつ書き、該当しない行は削除する
5. 索引をどこに置くかは、ドキュメントの数で決める。数個なら `README.md` の一節で足りる。`docs/` が階層化しているなら `docs/README.md` に索引を置き、`README.md` からはそこへ1行で送る

## いつ更新するか

**ドキュメントを追加・削除・移動したら、同じコミットで索引も更新する。** 別コミットに回すと必ず忘れる。索引と実体がずれた索引は、無い索引より悪い（存在しないファイルを読ませようとする）。
