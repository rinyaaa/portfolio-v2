# ワークツリー分割による並列実装

**既定は直列。** このスキルはユーザーが明示的に並列実行を求めたときだけ使う。並列エージェントは人数分だけ文脈を複製するので、トークン消費が最も大きい進め方であり、レビューも人数分発生する。「速そうだから」で選ばない。

## Step 1: 分割してよいか判定する

**分割する**: 独立して実装・レビュー・マージできる機能が2つ以上ある。

**分割しない（直列で進める）**——1つでも当てはまれば、その理由を伝えて直列を提案する。

- 機能が1つしかない
- 機能Aの設計・実装結果が決まらないと機能Bを書けない（依存がある）
- 複数の機能が同じファイル・同じレイヤーを大きく書き換える（コンフリクト解消のコストが並列化の利益を上回る）
- DBスキーマ変更（マイグレーション）を含む。**単独で先にマージしてから**他機能を始める

判定結果と理由は計画書の「並列化の単位」欄に書き、**人間の承認を得てからワークツリーを作る**。実装を始めてから思いつきで分割しない。

## Step 2: ワークツリーを作る

置き場所は**リポジトリ外の兄弟ディレクトリ**。リポジトリ内に置くと、ビルドツール・リンタの走査対象や、ルートの依存ディレクトリ・ローカルDBと干渉する。

```bash
REPO=$(basename "$(git rev-parse --show-toplevel)")
BASE=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|origin/||' || echo main)
git worktree add "../${REPO}-worktrees/<機能名>" -b "feature/<機能名>" "$BASE"
git worktree list
```

1ワークツリー = 1ブランチ = 1PR。並列数は5つまで。超える場合は人間に確認する（レビューが追いつかない）。

## Step 3: 各ワークツリーをセットアップする

**並列実行を始める前に必須。** ここを飛ばして「動かない」と報告しない。

1. **依存をインストールする。** 依存ディレクトリはワークツリー間で共有されない。ロックファイルでパッケージマネージャを判定する：`package-lock.json`→`npm ci`、`pnpm-lock.yaml`→`pnpm install`、`yarn.lock`→`yarn install`、`bun.lockb`→`bun install`、`uv.lock`→`uv sync`、`poetry.lock`→`poetry install`、`requirements.txt`→venv作成後 `pip install -r`、`Gemfile.lock`→`bundle install`、`go.sum`→`go mod download`
2. **ローカル状態はツリーごとに独立させる。** ローカルDB・キャッシュ・アップロード先などgit管理外のファイルは、実行時のカレントディレクトリ基準で別物になる。必要ならツリーごとにマイグレーション・初期データ投入を行う。**他のワークツリーのDBを参照・コピーしない**
3. **devサーバを同時起動するならポートをずらす。** 起動コマンドは `README.md` の「コマンド」を見る（このリポジトリはCLAUDE.md §7からそちらへ一本化してある）。ポートの指定方法が書かれていなければ、**推測でコマンドを組み立てず人間に聞く**。ポートが衝突したまま起動して「動かない」と報告しない
4. `.env` 等の設定ファイルはgit管理外なので新しいツリーには無い。**中身を読んでコピーしようとしない**（安全ルールでブロックされる）。必要なら、どのファイルを用意する必要があるかをユーザーに伝える

## Step 4: 並列で実装する

- 機能ごとに実装担当エージェントを1つ割り当て、**担当ワークツリーの中だけ**で作業させる。他のワークツリーやリポジトリ本体のファイルを触らせない
- 各エージェントに渡すのは、計画書のうち**その機能のスコープ / スコープ外 / 受け入れ条件**だけ。他機能の事情は渡さない
- 途中で他機能への依存が判明したら、勝手に他のワークツリーを触らず、**いったん止めて人間に報告する**
- 共通処理が必要になったら、独断でどちらかに寄せず人間に確認する。他機能のブランチを勝手に取り込まない
- `main` が進んだ場合の取り込みは `git merge`。`git rebase` や `git reset --hard` のような履歴・作業内容を書き換える操作は使わない

## Step 5: レビューと統合

`implementation-review` を**機能ごとに**適用する。別エージェントによるレビューの原則もループ上限5回も、機能ごとに数える。複数機能を1つのPRにまとめない。

## Step 6: 後始末（列挙するだけ）

タイミングは**その機能のPRがマージされ、`work-log` の記録を残したあと**。実装中・レビュー中・PR未マージのワークツリーは対象にしない。他機能の完了を待つ必要はなく、マージされた機能から順に片付けてよい。

**AIがやること**: 完了報告に、削除してよいワークツリーとブランチを列挙する。列挙前に各ツリーで `git status` を確認し、未コミットの変更が残っていればその旨も報告する。

```
削除してよいもの:
- ../<repo>-worktrees/<機能名> / ブランチ feature/<機能名>（PR #123 マージ済み・未コミットの変更なし）
```

**AIがやらないこと**: 削除コマンドの実行。`git worktree remove` / `prune` はファイルを実際に消す破壊的操作なので、`AGENTS.md` の安全ルールでブロックされている。人間に削除を依頼する。
