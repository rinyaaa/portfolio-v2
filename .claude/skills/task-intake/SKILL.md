# タスクの整理（Issue起票 / 計画書作成）

思いつきをそのまま書き出すのではなく、いくつかの観点で人間と一緒に理解を深めてから形にするスキル。目的は**着手前に曖昧さを削っておくこと**——実装を始めてからのスコープの揺れを防ぎ、特にこのタスクが将来 `night-run`(夜間自律実行)に渡ったとき、AIが夜中に自分で判断しなければならない余地をできるだけ減らしておく。

ヒアリングの中身は出力先によらず同じなので、このスキルに一本化してある。違うのは最後の出力先だけ。

- **GitHub Issue** — 後でやるタスク、他の人と共有するタスク、`night-run` に渡すタスク
- **計画書**(`docs/plans/`) — これから実装するタスク。実装方針とリスクまで書いて、承認を得てから着手する
- **両方** — 起票してそのまま着手する場合

判断するのは常にユーザー。このスキルは観点を提示して理解を深める補助であり、Claudeが単独で優先度や合否を決めるものではない。

## プランモードとの関係

Claude Codeのプランモードは「質問して曖昧さを潰す」「承認まで実装しない」という**進め方**を担い、その計画は `~/.claude/plans/` にセッション単位で保存されてリポジトリには残らない。このスキルが担うのは**成果物の型と置き場所**で、`docs/plans/` に残すのは合意済みでチームが後から参照する計画書だけ。進め方をここで書き直さない。

## Step 1: アイデアを聞く

やりたいこと・直したいことをユーザーから聞く。既に会話の中で十分語られていれば聞き直さなくてよい。

## Step 2: そもそも作るかを判断する

**次に当たるものは、Issueにも計画書にもしない。** そのまま実装するか、口頭で答える。

- タイポ・1行の修正・設定値の変更など、スコープを議論する余地がないもの
- 「これどうなってる？」のような調査・質問
- 既に会話の中でスコープと完了条件が合意できているもの

毎回ドキュメントを作ると、読み書きのコストだけが積み上がる。**迷う規模だけを対象にする。**

## Step 3: 既存タスクとの重複を確認する

GitHubを使っているプロジェクトなら `gh issue list --search "<キーワード>"` で似た既存issueが無いか確認する。`docs/plans/` があれば既存の計画書も見る。見つかったら、新規に作るか既存を更新するか、その場でユーザーに確認する。

## Step 4: 観点で理解を深める

以下の観点を、儀式的な採決としてではなく**会話の中で**確認していく。すべてを毎回フルに聞く必要はない——タスクの性質に応じて、明らかに関係ない観点は軽く流してよい。

- **Engineer観点**: 技術的に実現可能か。既存アーキテクチャ・コーディング規約(AGENTS.md/CLAUDE.mdに記載のもの)と整合するか。ざっくりの工数感。技術的負債にならないか
- **PM観点**: プロジェクトの優先順位付け基準(README.md等に定義があればそれに合わせる。無ければ「今すぐ/近いうち/余裕があれば」程度でよい)のどれに当たるか。スコープは適切か(大きすぎるなら分割を提案する)。他タスクとの依存関係はあるか
- **PO観点**: 受け入れ条件(完了の定義)を明確にできるか。誰にどんな価値があるか
- **Designer観点**: 既存のUI/UXパターンと一貫しているか(該当する場合のみ)。UIを伴うなら、まず `portfolio-design-source` スキルの手順でFigmaを確認し(見た目の正はFigma)、そのうえで `ui-guidelines` の制約(タッチ操作・コントラスト)を満たせるかを見る。未確定のデザインデータ(Skill一覧・Awards・SNSリンク等)に触れるタスクなら、この時点でユーザーに確認する
- **プロジェクト固有の専門観点(該当する場合のみ)**: ゲームなら面白さ・プレイフィール、ハードウェア連携ならデバイス互換性、など。プロジェクトの性質に応じて追加する。**体験・品質に関わる懸念が浮かんだ場合は、他の観点が問題無くても、それをそのまま流さずユーザーに明示的に提示し、一緒に解消してから次に進む**(「実装上は問題ないので起票します」で済ませない)。この観点をプロジェクトの絶対ルールにするかどうかは、`CLAUDE.md`/`AGENTS.md`に明記して固定するとよい。
- **SEO観点(このリポジトリでは必須)**: このportfolioは検索経由での被発見性(氏名・ニックネームでの検索露出)が目的の一つ。「どう実装するか(How)」を話し合う際は、そのタスクがSEOを**下げないか**を必ず確認し、上げられる余地があれば一言提案する(例: 新しいページを追加するなら `<title>`/meta description/構造化データを埋めるところまでタスクに含める、画像を追加するなら alt を書く、URLを変えるなら既存URLのリダイレクトを検討する、JSでしか表示されないコンテンツにしない等)。実装上問題なくてもSEO観点の懸念は流さず、他の観点と同様にユーザーに提示してから次に進む。

## Step 5: 出力先を決める

`AskUserQuestion` で「GitHub Issue / 計画書 / 両方」を選ばせる。会話の流れから明らかな場合(「これから作って」なら計画書、「忘れないうちに積んでおいて」ならIssue)は、その案を第一候補として提示する。

`gh` CLIが必要になるのはIssueを作る場合だけ。`gh auth status` で確認し、未導入なら `brew install gh && gh auth login` を案内する。**`gh` が無いことを理由にスキルごと諦めない**——計画書出力なら `gh` は要らない。

## Step 6: ドラフトをまとめる

Step 1〜4を踏まえてドラフトを作る。**共通の欄**:

- **タイトル**(番号は付けない。issue番号は`gh issue create`が自動採番するため、`#42`のような形でissue自体に付く)
- **背景・なぜやるか**
- **受け入れ条件(完了の定義)**: テスト可能な形で書く。「正しく動く」ではなく「◯◯を入力すると△△が返る」
- **スコープ**: 今回やること
- **スコープ外**: やらないことと、**なぜ対象外なのか**
- **優先度**: プロジェクトの優先順位付け基準に合わせる(Step 4のPM観点で確認したもの)
- **検討メモ**: 追加の専門観点などで話し合った内容(あれば。特に懸念とその解消内容は残す)

**計画書のときだけ足す欄**:

- **実装方針**: 変更するファイル / 追加するモジュール
- **並列化の単位**: 独立して実装・レビュー・マージできる機能が2つ以上あり、かつユーザーが並列実行を望む場合のみ。`parallel-worktree` スキルの判定基準に従って、分ける単位と理由(または直列にする理由)を書く。**既定は直列**なので、指示が無ければこの欄は「直列(機能が1つ / 依存があるため)」で足りる
- **想定リスク・確認事項**: 人間に確認が必要なポイント

Issueにはこの3欄を入れない(着手時に変わるため、起票時点で書くと陳腐化する)。

## Step 7: 確認する

ドラフトをそのまま提示し、`AskUserQuestion` で「この内容で確定する / 内容を直す / やめる」を確認する。直す場合はStep 4〜6に戻る。**承認されるまで実装に進まない。**

## Step 8: 出力する

### GitHub Issue の場合

1. `gh label list` で既存ラベルを確認する。優先度に対応するラベルが既にあれば使う。**無ければラベルを勝手に新規作成しない**——本文に優先度を書くだけに留め、ラベル運用を始めるかはユーザーに確認する
2. Step 6のドラフトをMarkdownの本文に整形する(見出しは`##`程度で十分)
3. `gh issue create --title "<タイトル>" --body "<本文>"`(該当ラベルがあれば`--label`も付ける)で作成する
4. 作成したissueのURL・番号をユーザーに伝える。あわせて、このタスクは今後 `night-run-hearing` から拾って夜間実行に回せることを一言添える(その際`night-run-hearing`側にはこのissue URLをそのまま渡せばよい)

### 計画書の場合

1. `docs/plans/YYYY-MM-DD-<タスクの短い名前>.md` に書き出す(日付は `date +%F` で取る)。ディレクトリが無ければ作る
2. 見出しはStep 6の欄をそのまま `##` の見出しにする（揃っていると `implementation-review` が差分と突き合わせやすい）
3. `docs/plans/README.md` があれば一覧に1行追加する
4. パスをユーザーに伝え、実装に進んでよいか確認する

### 両方の場合

Issueを先に起票し、計画書の冒頭に そのissue URL を記載してから計画書を書き出す。
